# Global Commonsense Generalization

## Terminology and Schema Compatibility

Each source item is **instance-level commonsense**. The rule serialized as
`base_unit` is a **generalized commonsense rule**. A complete object containing
that rule, its members, variant deltas, and rationale is a **commonsense
generalization record**.

Legacy JSON keys such as `candidate_families`, `rule_families`, `family_id`,
`base_unit`, and `member_ids` are retained for schema compatibility. Emit them
exactly as specified, while applying the terminology above when reasoning.

## Background

You are given one candidate group of previously produced commonsense generalization records. The candidate group was produced by semantic retrieval, reranking, graph construction, and preliminary grouping. These earlier stages only narrowed the search space. They do not establish that all supplied records or source items belong together.

Each previous family has a provisional `base_unit`. Each source unit was originally extracted from an individual GUI software issue and expresses a normative expectation about software behavior in a recurring situation.

Your task is to re-evaluate the expanded instance-level commonsense items and produce the final commonsense generalization records. You may merge items across previous records, split a previous record, retain only part of a previous record, create multiple final records, or omit items that cannot be safely grouped.

## Input

The input is one JSON object containing `candidate_families` and `source_units`.

Each item in `candidate_families` contains:

- `id`: a short batch-local family alias such as `F0`;
- `base_unit.situation`: the provisional recurring situation of the previous family;
- `base_unit.commonsense_rule`: the provisional expectation of the previous family.

Each item in `source_units` contains:

- `id`: a short batch-local source-unit alias such as `U0`;
- `prior_family_id`: the candidate-family alias from which the source unit was expanded;
- `situation`: the abstract, recurring operational context in which the expectation applies, especially the relevant operations and their temporal, causal, or state-transition relationships;
- `commonsense_rule`: the expected behavior or prohibited failure expressed by the source unit;
- `applicability_conditions`: auxiliary evidence about when the source rule applies.

Treat all IDs as opaque reference tokens. Copy a source-unit ID exactly when using it in the output. Do not infer semantics from an ID, alter it, invent an ID, or attempt to recover an external identifier.

## Evidence and Authority

The `source_units` are the authoritative semantic evidence.

The candidate-family bases are provisional summaries generated by an earlier model. They may help identify possible shared invariants, but they may be too broad, too narrow, incomplete, or incorrect. Do not preserve, copy, or trust a candidate base unless every included source unit independently supports it.

`prior_family_id` records provenance only. It is not semantic evidence and does not require units from the same previous family to remain together. Source units from different previous families may be placed in one final family, and source units from one previous family may be split among different final families or omitted.

Use `applicability_conditions` only as auxiliary evidence when deciding whether source units have compatible scope. Never copy, paraphrase, summarize, generalize, or transfer information from `applicability_conditions` into any output field. Every generated base or delta statement must be independently supported by a source unit's `situation` or `commonsense_rule`. If an applicability condition reveals an incompatibility that cannot be represented using those core fields, separate or omit the affected unit.

## Goal

Organize compatible source items into final commonsense generalization records.

A valid record is a loss-aware representation of source items that express either the same atomic expectation or the same specific, testable design invariant. It contains:

1. a reusable `base_unit` supported by every member;
2. `equivalent_member_ids` for source units that express the same essential rule as the base;
3. `variant_groups` for source units that preserve the base but add meaningful situation or behavioral details;
4. one shared `delta` for every group of mutually equivalent variants;
5. a concise `family_rationale` explaining the substantive invariant shared by all members.

Do not force all input units into families. A final family must contain at least two distinct source units. Omit source units that do not belong to a valid family; the calling program will treat them as singletons.

## Core Concepts

### 1. Base Unit

The `base_unit` contains exactly:

- `situation`: the reusable operational situation or relationship shared by all family members;
- `commonsense_rule`: the expected behavior or protected property shared by all family members.

Every semantic element in the base must be supported by every member. Support from only some or most members is insufficient. Information unique to particular members belongs in their deltas, or those members must be separated.

The base must be:

- specific enough to state a meaningful and testable expectation;
- general only to the extent supported by every member;
- atomic, with one primary normative expectation;
- independently understandable;
- free of issue-specific, project-specific, and incidental details.

Do not create vague bases such as "the interface should work correctly", "the application should behave as expected", or "the software should provide a good user experience". Do not infer universal scope from a finite set of examples or introduce unsupported subjects, objects, behaviors, conditions, exceptions, or quantifiers.

A delta can add source-specific information, but it cannot remove or correct unsupported information in the base. If a proposed base contains a situation or behavior element absent from one member, remove that element from the base and place it in the appropriate variant delta only for members whose core `situation` or `commonsense_rule` explicitly supports it. If no meaningful shared base remains, split or reject the family. Never use a delta to negate, replace, narrow, or repair the base for a member that does not support it.

### 2. Design Invariant

A design invariant is a specific, testable property that software should preserve across related concrete situations. Members may realize or violate it through different concrete behaviors, provided those differences can be added to the base through deltas.

For example, rules requiring a signed-number field to accept a negative sign and a case-sensitive token field to accept mixed-case characters may share this invariant:

> An input control should accept every character that is valid for its expected data format.

This is a valid shared principle because it identifies the affected object, the relevant situation, and the property that must be preserved. In contrast, statements such as "input should work correctly" or "the interface should be user-friendly" are not design invariants: they are broad quality claims that do not state a testable shared expectation.

Use the most specific meaningful invariant supported by all family members. Do not group units merely because they concern the same component, domain, user goal, or general quality attribute.

### 3. Delta

A `delta` is the semantic difference between a variant source unit and the family's `base_unit`. It contains only the material information expressed by the source unit that is not already expressed by the base.

It has exactly two fields:

- `situation_differences`: variant-specific operations, triggers, interaction sequences, restrictions, or state-transition relationships not expressed by the base situation;
- `commonsense_rule_differences`: variant-specific required behavior, prohibited outcome, mechanism, refinement, or additional obligation not expressed by the base rule.

Each field is an array of concise strings. A delta item must describe only the difference from the corresponding base content. Do not copy or paraphrase the complete source situation or rule when the base already expresses that information. Derive `situation_differences` only from the source unit's `situation`, and derive `commonsense_rule_differences` only from its `commonsense_rule`. Never derive either field from `applicability_conditions`. If applicability conditions reveal a material compatibility problem, separate or omit the affected units instead of transferring that information into a delta.

The delta is not a second canonical unit and must not contain a complete rewritten variant unit. The original source unit remains available through `member_ids`; the delta only explains what distinguishes that variant from the base.

A delta may add source-supported differences to the corresponding base fields. It must never negate, contradict, replace, narrow, or correct the base. Every statement in the base must already be supported by every family member. If a member does not support a base statement, revise the base to the true shared semantic intersection or split the family rather than using a delta to repair the mismatch.

Evaluate the two delta fields independently. If a source unit adds a situation-specific trigger or restriction but no material behavior beyond the base rule, `commonsense_rule_differences` must be empty. Likewise, if only the expected behavior differs, `situation_differences` may be empty. Do not repeat base behavior merely to make a situation-specific delta read like a complete standalone rule.

Every variant-group delta must contain at least one non-empty array. Units with no meaningful delta belong in `equivalent_member_ids`, not `variant_groups`.

Source units may share one `variant_group` only when they are mutually equivalent and have exactly the same semantic delta from the base. Otherwise, place them in separate variant groups. A variant group may contain one source ID.

The base does not need to match one source unit exactly. If the base is a shared abstraction, `equivalent_member_ids` may be empty and all members may be represented through variant groups. In that case, the base must still be the narrowest meaningful invariant supported by every member.

### 4. Member Representation

Place a source ID in `equivalent_member_ids` when the source unit has the same essential situation scope, expected behavior, and prohibited failure as the base after ignoring only wording and incidental details.

The base alone must faithfully represent every equivalent member. Do not create an empty delta for an equivalent member.

Source units that preserve the base but add meaningful information belong in `variant_groups` under the rules above. The `family_rationale` must briefly identify the substantive atomic rule or design invariant shared by all members and explain why their differences can be represented as additions to the base rather than replacements or contradictions.

## Reconstruction Test

For every included source unit, the base plus that source unit's delta, if any, must faithfully reconstruct the essential meaning of its original `situation` and `commonsense_rule`.

Verify both directions:

1. **Completeness:** every material operation, relationship, restriction, expected behavior, and prohibited outcome in the source unit is represented by the base or its delta.
2. **No unsupported additions:** every material statement in the reconstructed meaning is supported by that source unit.

For an equivalent member, apply the test to the base alone. For a variant member, apply it to the base plus the shared delta of its variant group.

If reconstruction loses information, adds unsupported meaning, changes when a rule applies, or requires negating or replacing the base, revise the base or delta, split the group, remove the source unit, or reject the family.

## Family Membership

Create one family when its members share the same non-trivial atomic expectation or specific design invariant, including cases where:

- the units are duplicates or paraphrases;
- one states a general expectation and another applies it in a narrower situation;
- the units require the same outcome through different concrete mechanisms;
- one unit preserves the shared expectation and adds another requirement;
- different concrete behaviors preserve the same specific, testable property;
- different failure manifestations violate the same specific invariant and their differences can be preserved by deltas.

Do not create one family when:

- the only commonality is a topic, feature, object, component, workflow, or keyword;
- the proposed base would be vague or non-actionable;
- the units protect different underlying properties;
- their situations are incompatible;
- their expected behaviors conflict under overlapping situations;
- representing a member requires replacing or contradicting the base;
- a delta would contain most of the original rule because little meaningful content is shared;
- grouping would hide a distinction that materially changes when the expectation applies;
- the relationship is uncertain.

Every family must be coherent as a whole. Do not form a family through a similarity chain in which adjacent units are related but no single substantive invariant is supported by every member.

## Required Procedure

1. Use the candidate bases only to identify hypotheses worth checking.
2. Independently analyze every source unit's recurring situation, operational relationships, expected behavior, and prohibited failure.
3. Check whether each previous family is internally coherent; do not assume it should remain intact.
4. Identify candidate source-unit groups, including possible groups across previous-family boundaries.
5. Propose the most specific meaningful base supported by every member of each candidate group.
6. Reject a group whose shared base is vague, unsupported, contradictory, or merely topical.
7. Separate base-equivalent source units from variants.
8. Partition variants so that all IDs in one variant group are mutually equivalent and share exactly the same delta.
9. Apply the bidirectional reconstruction test independently to every included source unit.
10. Ensure that no source ID appears in more than one final family.
11. Omit uncertain or ungrouped source units.

## Examples

The IDs in these examples are illustrative and must never be copied into the actual output.

### Example A: General Rule and Situation-Specific Variant

Input meanings:

- `EXAMPLE_1`: pasted content should be preserved completely;
- `EXAMPLE_2`: pasted Unicode content should be preserved completely.

Valid family:

```json
{
  "base_unit": {
    "situation": "pasting clipboard content into a destination that accepts text",
    "commonsense_rule": "Pasting should preserve the complete copied content without truncation or data loss."
  },
  "equivalent_member_ids": [
    "EXAMPLE_1"
  ],
  "variant_groups": [
    {
      "member_ids": [
        "EXAMPLE_2"
      ],
      "delta": {
        "situation_differences": [
          "The pasted content contains Unicode or multi-byte characters."
        ],
        "commonsense_rule_differences": []
      }
    }
  ],
  "family_rationale": "Both units require complete preservation of pasted content; the second unit restricts the content type."
}
```

The Unicode variant does not add a new expected behavior, so its `commonsense_rule_differences` is empty. Do not repeat the base's content-preservation requirement in that field.

### Example B: Base Behavior with an Additional Requirement

Input meanings:

- `EXAMPLE_3`: opening a navigation overlay should dismiss the virtual keyboard;
- `EXAMPLE_4`: opening a navigation overlay should dismiss the virtual keyboard and obscure the underlying interface.

These units may share the keyboard-dismissal base. Put `EXAMPLE_3` in `equivalent_member_ids`. Put `EXAMPLE_4` in a single-member `variant_group`, with only the additional requirement to obscure the underlying interface recorded under `delta.commonsense_rule_differences`. Do not place `EXAMPLE_4` in `equivalent_member_ids`, and do not repeat keyboard dismissal in its delta.

### Example C: Equivalent Variants Sharing One Delta

Input meanings:

- `EXAMPLE_5`: pasting Unicode text should preserve all copied content;
- `EXAMPLE_6`: Unicode clipboard content should be pasted without truncation or loss;
- `EXAMPLE_7`: pasting ordinary text should preserve all copied content.

If `EXAMPLE_5` and `EXAMPLE_6` are equivalent formulations of the same Unicode-specific rule, place them together in one `variant_group.member_ids` array with the Unicode-content restriction as their shared `situation_differences`. If `EXAMPLE_7` is equivalent to the family base, place it in `equivalent_member_ids`.

### Example D: Same Object but Different Rules

Input meanings:

- a virtual keyboard should use the correct language layout;
- a virtual keyboard should not cover selectable suggestions;
- opening a virtual keyboard should not change display orientation.

Do not place these units in one family. They concern the same object but express different normative expectations. A base such as "the virtual keyboard should behave correctly" would be invalid because it is vague and non-actionable.

### Example E: Do Not Absorb Variant-Only Information into the Base

Input meanings:

- `EXAMPLE_8`: changing a media player's display mode should preserve the current playback position;
- `EXAMPLE_9`: connecting a peripheral during playback should preserve the playback position and should not interrupt playback.

An invalid base would enumerate both "changing display mode" and "connecting a peripheral" while placing `EXAMPLE_8` in `equivalent_member_ids`. The peripheral operation is not supported by `EXAMPLE_8`, so the base alone would no longer reconstruct it faithfully.

If the units are grouped, use only a narrow shared invariant supported by both, such as preserving playback position during a non-transport interaction. Because neither source expresses that base at exactly the same situation scope, `equivalent_member_ids` should be empty. Put each source in its own variant group, record its specific interaction under `situation_differences`, and record interruption prevention under `EXAMPLE_9`'s `commonsense_rule_differences` only. If that shared abstraction is not sufficiently supported, keep the units separate.

## Output Schema

Return exactly one JSON object with this structure:

```json
{
  "rule_families": [
    {
      "base_unit": {
        "situation": "...",
        "commonsense_rule": "..."
      },
      "equivalent_member_ids": [
        "U0",
        "U2"
      ],
      "variant_groups": [
        {
          "member_ids": [
            "U1",
            "U3"
          ],
          "delta": {
            "situation_differences": [
              "..."
            ],
            "commonsense_rule_differences": []
          }
        }
      ],
      "family_rationale": "..."
    }
  ]
}
```

## Output Requirements

- Return one valid JSON object and no other text.
- The root object must contain exactly `rule_families`.
- Every family object must contain exactly `base_unit`, `equivalent_member_ids`, `variant_groups`, and `family_rationale`.
- Every `base_unit` must contain exactly `situation` and `commonsense_rule`, both as non-empty strings.
- `family_rationale` must be a concise, non-empty string identifying the substantive shared invariant and why the member differences can be represented additively.
- Use only source-unit IDs from `source_units` in membership fields.
- Never output candidate-family IDs, `prior_family_id` values, invented IDs, final family IDs, batch IDs, singleton records, counts, confidence scores, or processing metadata.
- Each final family must contain at least two distinct source-unit IDs across `equivalent_member_ids` and all `variant_groups[].member_ids`.
- `equivalent_member_ids` must contain distinct IDs and may be empty only when no source unit matches the base at the same semantic scope.
- Every variant group must contain exactly `member_ids` and `delta`.
- Every `member_ids` value must be a non-empty array of distinct source-unit IDs.
- Every delta must contain exactly `situation_differences` and `commonsense_rule_differences`.
- Every delta item must be a concise, non-empty string stating only information absent from the corresponding base field.
- A variant delta must have at least one non-empty difference array.
- No source-unit ID may appear more than once within a family or in more than one family.
- Omit source units that do not belong to a valid family instead of reporting them.
- Do not output old-to-new family mappings, split decisions, pairwise relations, similarity judgments, conflicts, or unrelatedness records.
- Do not transfer information from `applicability_conditions` into any output field.
- Before returning, verify the base-plus-delta reconstruction for every included source unit.
- If no valid family exists, return `{"rule_families": []}`.
